# 15W 模式 RTSP／YOLO 同步與封包測試

測試日期：2026-09-24（Asia/Taipei）。`rtsp_yolo_direct` 透過 UDP 接收
`rtsp://192.168.144.135/live`，本機 Chrome 播放；Jetson 電源模式為 15W。
同時以 `dumpcap` 在 `eth1` 擷取相機 IP 的封包，snaplen 512 bytes。

## 同步結果

- 正式測試跑滿 1,200 秒、1,201 筆逐秒取樣，但來源影像只持續到約
  1,122 秒（18 分 42 秒），因此不是連續 20 分鐘的有效影像測試。
- 1,127 筆有影片／YOLO 來源 PTS 可配對。差距中位數 33.38 ms、
  P95 100.11 ms、P99 166.84 ms、最大 200.21 ms；沒有樣本超過
  250 ms，也沒有觀察到同一 generation 內影片 PTS 倒退。
- 0–5、5–10、10–15、15 分鐘至中斷前，各段中位數都是 33.38 ms，
  沒有看到差距隨時間累積。
- RTSP 在來源停止後重試 7 次，直到測試結束都沒有恢復影像。

## 封包時間線

- 14:25:51 前，來自相機的 UDP 封包約每秒 180–210 個。之後媒體封包
  停止；伺服器逐秒計數也在 14:25:52 停住。此時沒有先收到 RTCP BYE。
- 14:26:01.999，**Jetson 客戶端先送出 RTSP TEARDOWN** 並關閉原 TCP
  連線；14:26:02.001，相機才回送 RTCP BYE。這個 BYE 是客戶端逾時
  清理連線後的回應，不能解讀為造成最初停流的相機主動 BYE。
- 後續每次重連，相機都對 OPTIONS、DESCRIBE、SETUP、PLAY 回覆
  `RTSP/1.0 200 OK`，但沒有恢復 RTP 影像。各次約 10 秒後由客戶端
  TEARDOWN，相機再回 BYE。
- `dumpcap` 統計擷取 231,734 個封包，介面／擷取器丟包皆為 0。

這次證據顯示網路控制連線在影像停止後仍能與相機往返，較不像整條
網路線完全斷開；但仍無法單靠封包擷取區分相機內部停止編碼／送流、
電源接觸問題或只影響媒體封包的鏈路故障。

逐秒資料見 `samples.jsonl`、彙總見 `summary.json`；原始網路封包在
`../direct_sync_20260924_packet_capture/`，可用
`python diagnostics/analyze_camera_pcap.py <pcapng 檔>` 重現封包摘要。
